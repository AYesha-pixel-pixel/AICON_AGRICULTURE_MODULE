## API contract checks

The canonical FastAPI application was checked with `TestClient` and OpenAPI
generation:

- `GET /` returns a lightweight landing response and does not load the model.
- `GET /health` reports process status and leaves `model_ready` as `null`
  without a deliberate readiness probe.
- `GET /crops` returns only configured selectable crops.
- `POST /analyze` validates image content through the existing validator,
  reuses the cached model service, applies existing decision rules, and
  returns an analysis reference.
- `POST /advisory` accepts only a server-generated analysis reference and
  blocks non-usable decisions before any Gemini call.
- Internal model/provider failures are mapped to sanitized HTTP errors.

The analysis-reference store is suitable for local development only. A
production deployment with multiple workers or restart tolerance needs a
shared, access-controlled store with expiration and deletion policy.

## Gemini and secret handling

The advisory service reads `GEMINI_API_KEY` and `GEMINI_MODEL` from the
environment. The key is not embedded in source, tests, documentation, or API
responses. The Gemini SDK is optional to normal image analysis: `/`, `/health`,
`/crops`, and `/analyze` remain independent of advisory availability.

The provider boundary validates structured output, discards model-authored
sources unless grounding metadata contains validated sources, and never
returns raw provider exception details. Uncertain, unsupported, invalid, and
crop-mismatched results do not trigger disease-specific Gemini requests.

## Weather findings

The repository contains a canonical weather route plus a retained separate
weather service:

1. `src/weather_service.py`, a direct Open-Meteo library function.
2. `api.py`, the primary FastAPI application with `/api/weather`.
3. `backend/main.py`, a retained separate weather FastAPI service with `/` and
   `/api/weather`.

Both API paths use a 10-second request timeout through their respective
implementations. The canonical route is the one frontend clients should use.
Weather remains optional to image analysis, and the advisory endpoint accepts
optional weather context supplied by the caller rather than fetching weather
automatically. The separate backend should not be started alongside the
canonical server on port 8000.

## Agricultural evidence and safety

The code does not provide pesticide names, chemical dosages, spray schedules,
or guaranteed yield claims. Knowledge and guidance entries remain explicitly
marked for local verification where the source registry does not support a
specific claim. A model result is presented as preliminary decision support,
not a confirmed field diagnosis.

## Model performance

The images under `samples/` are smoke-test assets. `test_results.csv` contains
predictions without ground-truth labels. There is no suitable labelled local
manifest in the repository, so measured accuracy, precision, recall, F1, and
confusion-matrix performance remain unknown.

## Remaining blockers and prioritized next steps

1. Supply a documented, permissioned, labelled held-out evaluation manifest;
   then run `evaluate_model.py` without tuning thresholds on that split.
2. Decide whether weather should be fetched automatically for advisory
   requests or remain caller-supplied context; the canonical weather route and
   normalized contract are already available.
3. For production advisory use, provide an approved Gemini deployment secret
   through a secret manager and validate one bounded live request.
4. Replace the in-memory analysis-reference store before using multiple API
   workers or requiring references to survive restarts.
5. Complete local agricultural review of disease knowledge before treating
   any disease-specific field as verified.
